      APCSP 备考手册 · Big Idea 1 创造性开发（Creative Development，CRD）

      依据 College Board《AP Computer Science Principles Course and Exam Description》（2023 CED）编写
      适用考试：AP CSP 国际考（End-of-Course Exam：Section I 70 道 MCQ + Section II 4 道写作题）

      0. 本章定位：Big Idea 1 考什么、怎么考

      0.1 考试权重

      Big IdeaMCQ 权重

      Big Idea 2：Data17–22%
      Big Idea 3：Algorithms and Programming30–35%

      Topic名称核心 Learning Objective常见考查方式

      • CRD-1：通过协作吸纳多种视角（multiple perspectives）能改进计算创新。
      • CRD-2：开发者以用户为中心（user-focused）、经历"实现—反馈"循环（implementation/feedback cycles）、留有实验与冒险空间的迭代设计过程来创造和创新。

      1. Topic 1.1 Collaboration（协作）

      1.1 知识点梳理（CRD-1.A / 1.B / 1.C）

      条目内容
      CRD-1.A.1计算创新（computing innovation）：以程序为其功能的不可分割部分的发明（包括硬件+程序+概念）
      CRD-1.A.2计算创新可以是有形的（自动驾驶汽车）、无形的软件（修图软件）或无形的概念（电子商务）
      CRD-1.A.3有效协作产生的创新能反映设计者多元的才能与视角（diversity of talents and perspectives）
      CRD-1.A.4包含多元视角的协作有助于避免偏见（avoid bias）
      CRD-1.A.5与用户的咨询和沟通（consultation and communication）是开发计算创新的重要环节
      CRD-1.A.6从潜在用户处收集的信息可用于从多元视角理解程序目的，并开发出充分吸纳这些视角的程序
      CRD-1.B.1在线工具支持协作：共享和反馈想法与文档（共享文档、云文件夹、视频会议等）
      CRD-1.B.2常见协作模式：如 pair programming（结对编程）
      CRD-1.C.1高效协作团队需要人际技能（interpersonal skills）：communication 沟通、consensus building 达成共识、conflict resolution 化解冲突、negotiation 协商

      1.2 重难点

      1. 协作的"收益清单"要背牢——考题常问"以下哪项不是协作的好处"：
      • ✅ 减轻个人任务量、降低单个任务的规模和复杂度
      • ✅ 多人更容易发现和纠正错误（多一双眼睛）
      • ✅ 带来多元视角，激发创意
      • ✅ 帮助预判各类用户的需求、减少偏见
      • ❌ 绝不消除"意见分歧"——分歧恰恰需要 conflict resolution 去解决
      • ❌ 绝不免除软件测试
      • ❌ 绝不减少对文档的需求
      1. "多元视角→减少偏见"是 CRD-1 的主旋律：2025、2026 年连续两年考到"咨询多元化用户群体→减少算法/软件中的偏见"。

      1.3 易错点

      • 绝对化动词 = 错误选项：eliminate（消除）、remove the need for（免去）……凡宣称协作能"免去测试/免去文档/消除分歧"的选项几乎必错。
      • "各写各的再合并"不算高效协作：多人独立写代码、最后由一人拼合，缺少沟通与反馈，是"最不可能促进协作"的典型选项（真题重复考查）。
      • 在线协作工具（共享文档、云文件夹、视频会议）是促进协作的正面例子。

      2. Topic 1.2 Program Function and Purpose（程序功能与目的）

      2.1 知识点梳理（CRD-2.A ~ 2.D）

      条目内容
      CRD-2.A.1计算创新的目的（purpose）：解决问题（solve problems）或通过创意表达追求兴趣（pursue interests through creative expression）
      CRD-2.A.2理解创新目的能让开发者更好地开发该创新
      CRD-2.B.1程序（program）= 一组程序语句（program statements）的集合，运行时执行特定任务；常被称为软件（software）
      CRD-2.B.2代码段（code segment）= 程序的一部分语句集合
      CRD-2.B.3程序必须在多种输入和情境下都能工作
      CRD-2.B.4程序的行为（behavior）= 程序运行时如何起作用，常从"用户如何与之交互"的角度描述
      CRD-2.B.5描述程序可"宽"（它做什么 what it does）也可"细"（做什么 + 语句如何实现 how the statements accomplish it）
      CRD-2.C.1输入（input）= 送入计算机供程序处理的数据；形式多样：触觉、音频、视觉、文本
      CRD-2.C.2事件（event）= 与某个动作关联、给程序提供输入数据的东西
      CRD-2.C.3事件可由按键、点击鼠标、程序启动等任何影响执行流的已定义动作触发
      CRD-2.C.4输入通常会影响程序产生的输出
      CRD-2.C.5事件驱动编程（event-driven programming）：语句被触发时执行，而非按顺序控制流执行
      CRD-2.C.6输入可来自用户或其他程序
      CRD-2.D.1输出（output）= 程序发送到设备的数据；形式：触觉、音频、视觉、文本
      CRD-2.D.2输出通常取决于程序的输入或先前的状态（prior state，如内部变量值）

      2.2 重难点：识别"必需的输入"（近三年最高频题型）

      阅读材料题组（reading passage，2023 CED 明确规定 MCQ 含一组 5 道材料题）几乎每年都有一道"以下哪个数据是程序必需但不是从某用户设备收集的"。

      解题三步法：

      1. 回到材料找"程序要完成的功能"（如：推荐餐厅、分享跑步路线、主持视频会议）；
      2. 逐项问："没有这个数据，功能能不能完成？"——不能完成的就是必需输入；
      3. 再判断该数据"由谁提供"：来自题目主人公的设备？还是来自其他用户/其他程序/公司自己的数据库？

      典型例证（均来自国际考真题，见第 6 节）：

      • RunRoutr 分享 Adrianna 的跑步路线 → 需要"其他用户的当前位置"（不是从 Adrianna 手机取得的）；
      • 视频会议应用主持会议 → 需要"被邀请者是否接受会议"的信号（来自其他用户的设备）。

      2.3 易错点

      • "描述程序"的宽窄之分：只说"做什么"是宽泛描述；"做什么+语句如何实现"才是详细描述。选项混搭时要看清问的是哪一种。
      • 输出不只来自输入：还取决于 prior state（程序内部已有的变量值），只看输入推输出会出错。
      • 事件驱动的程序中，执行顺序由触发决定，不是从上到下顺序执行。
      • 输入不仅来自"人的操作"，也可来自传感器（GPS、麦克风、摄像头）和其他程序。

      3. Topic 1.3 Program Design and Development（程序设计与开发）

      3.1 知识点梳理（CRD-2.E ~ 2.H）

      条目内容
      CRD-2.E.1开发过程可以有序且有意图（ordered and intentional），也可以是探索式（exploratory）
      CRD-2.E.2常见开发阶段：investigating and reflecting（调查与反思）→ designing（设计）→ prototyping（原型）→ testing（测试）
      CRD-2.E.3迭代（iterative）过程：基于反馈、测试或反思不断细化与修订，可能回到早期阶段
      CRD-2.E.4增量（incremental）过程：把问题拆成小块，每块验证可用后再加入整体
      CRD-2.F.1程序设计包含调查（investigation）以确定需求
      CRD-2.F.2调查有助于了解程序约束（constraints）及使用者的关切和兴趣
      CRD-2.F.3调查方式：问卷调查（surveys）、用户测试（user testing）、访谈（interviews）、直接观察（direct observations）
      CRD-2.F.4程序需求（requirements）描述程序如何运作，包括必须提供的用户交互
      CRD-2.F.5程序的规格说明（specification）定义程序的需求
      CRD-2.F.6设计阶段（design phase）说明如何实现规格说明
      CRD-2.F.7设计阶段可包括：头脑风暴、计划与故事板（storyboarding）、按模块/功能组件组织程序、绘制用户界面示意图、制定测试策略
      CRD-2.G.1程序文档（documentation）：对代码段/事件/过程/程序的功能及其开发过程的书面描述
      CRD-2.G.2注释（comments）：写进程序里给人看的文档形式，不影响程序运行
      CRD-2.G.3应贯穿开发全程写文档
      CRD-2.G.4文档帮助个人或协作环境下开发与维护正确程序
      CRD-2.G.5并非所有编程环境都支持注释，可能需要其他文档方式
      CRD-2.H.1必须致谢（acknowledge）协作开发或来自他人的代码段
      CRD-2.H.2致谢可写在程序文档中，须注明来源或原作者姓名（2023 CED 补充：AI 工具生成的代码也须以注释注明，如 "This code was generated using [tool name]"）

      3.2 重难点

      1. 迭代 vs 增量（概念辨析高频）：
      • 迭代 = 反复"实现→反馈→修订"，可能回头重做；
      • 增量 = 化整为零，每块先跑通再加；
      • 二者的共同好处（真题答案原话）：帮助程序员在向可运行程序逐步添加组件时及早发现错误（identify errors as components are added to a working program）。
      1. 文档三连问（概念题固定套路）：
      • 文档写完后还能改吗？→ 能，程序修改时文档也要更新；
      • 程序完成后还需要文档吗？→ 需要（维护、修改时都有用）；
      • 只有团队开发才需要文档吗？→ 不是，个人开发同样需要。
      1. 为什么把重复代码封装成 procedure？→ 减少重复代码、提高可读性、便于维护（修改一处即可）；它不能提高运行速度、不能减少输入数据、不能降低用户输错率。

      3.3 易错点

      • 调查阶段收集用户数据时，抽样方式决定偏见：只问"离公司近的 10 个用户/最活跃玩家/开发者的朋友"→ 样本不具代表性（not representative / may not reflect all potential users）；从全体用户中随机抽取→ 最不易引入偏见。
      • "需求（requirements）"是调查的产出，"设计（design）"是如何满足需求——两者因果别颠倒。
      • 注释写给人看，删除或添加注释不改变程序行为；但 Create PT 的 Personalized Project Reference 截图中不得包含注释或课程内容（会被判 0 分）——这是考试规则，不是语法规则，注意区分。

      4. Topic 1.4 Identifying and Correcting Errors（识别与纠正错误）

      4.1 知识点梳理（CRD-2.I ~ 2.J）

      四类错误（必背）：

      错误类型定义典型例子
      Logic error 逻辑错误算法/程序中的错误导致行为不正确或出乎意料（程序能跑）条件写反、循环边界差一、交换两个变量次序错误
      Syntax error 语法错误违反编程语言规则的错误（跑不起来）缺括号、缺引号、关键字拼错
      Run-time error 运行时错误程序执行期间发生的错误（各语言自定义）除以零、访问越界索引、死循环后内存耗尽
      Overflow error 溢出错误计算机试图处理超出定义范围的数8 位无符号整数 255+1→0；有符号整数溢出后变成负数

      发现和纠正错误的有效手段（CRD-2.I.5，五个都要认识）：
      test cases（测试用例）、hand tracing（手工跟踪）、visualizations（可视化）、debuggers（调试器）、adding extra output statement(s)（加输出语句/DISPLAY 调试）。

      测试（CRD-2.J）：

      • 测试用定义好的输入（defined inputs）验证程序是否产生预期输出，据结果修订程序；
      • 定义输入应展示各种预期结果，或取恰好在/略超出极值（minimum 和 maximum）的输入——即边界值（edge cases）；
      • 需要依据程序需求来选择合适的测试输入。

      4.2 重难点

      1. Overflow vs Round-off（最高频混淆点）：
      • 整数太大存不下 → overflow（8 位存 200+60=260 → 变成 4；3 位存 5+3=8 → 变成 0；播放量 200 万变成七位负数 = 有符号溢出）；
      • 实数精度不够 → round-off（0.5 − 0.4 − 0.1 ≠ 0，浮点误差）；
      • 判断口诀：整数场景想溢出，小数偏差想舍入。
      1. "一次测试通过 ≠ 程序正确"：真题原话——用一个测试用例得出"程序正确"的结论是不充分的（not sufficient）；测试应覆盖不同预期结果，尤其是边界。
      2. "证明程序有错"只需一个反例：问"以下哪组初值能证明代码不正确"，选让逻辑漏洞暴露的那组（如求 max(x,y,z) 的嵌套 IF 只比较了部分组合时，选"x=1, y=3, z=2"这类让中间值最大/某变量从未被比较的组合）。
      3. 逻辑错误修复三板斧（代码题套路）：
      • 循环变量更新位置不对（先自增再使用 / 忘记更新 → 死循环）；
      • IF/ELSE 分支写反或 RETURN 值写反（isIncreasing 返回 true/false 互换）；
      • 多个独立条件用并列 IF 时，同时命中的数据被重复计数（如"被 2 或 7 整除"的计数题）。

      4.3 易错点

      • 死循环（infinite loop）属于 run-time 表现，最常见的语法层面原因是忘记更新循环变量或更新位置错误——补一条 index ← index − 1 / index ← index + 1 的位置题是送分题，注意"放在 IF 内还是 IF 外"。
      • REPEAT UNTIL 的条件是"退出条件"（满足即停），REPEAT UNTIL(i > 10) 执行到 i=11 才停；把它与"执行 10 次"划等号前先数一遍。
      • 删除列表元素后再访问原索引会错位；从后往前（index 从 LENGTH 递减）遍历删除是安全套路。
      • RANDOM(1,4) 两次独立调用结果互不相干——用两次 RANDOM 模拟互斥事件（25%/75%）会漏计试验，正确改法是把第二个 IF 改成 ELSE。

      5. 重难点与易错点速查表（考前 10 分钟过一遍）

      #考点一句话结论
      1协作收益带来多元视角、减少偏见、易找错；不免测试、不免文档、不消分歧
      2多元用户反馈随机抽样才不易引入偏见；亲友/最活跃用户/附近 10 人 = 偏差样本
      3程序目的解决问题 或 创意表达
      4输入/输出输入可来自用户、传感器、其他程序；必需但"非本设备收集"的输入是高频题
      5事件驱动由触发决定执行，非顺序执行
      6开发阶段调查反思 → 设计 → 原型 → 测试，迭代可回溯、增量分块验证
      7迭代/增量好处向可运行程序逐步添加组件时及早发现错误
      8文档/注释全程书写、随时更新、个人也需要；注释不影响运行
      9引用致谢他人代码、AI 生成代码都要注明出处
      10四类错误整数超范围=溢出（可能变负）；小数偏差=舍入；违反语法=语法错；运行中崩溃=运行时错
      11测试充分性一个用例通过≠正确；要测边界值和不同预期结果
      12反例证明证明"程序有错"只需一组让错误暴露的数据
      13重复计数并列 IF 处理互斥条件时，交集数据被算两次

      • (C) 2,3,1：IF1 假；IF2 中 3>2 真、3>1 真 → max←3 ✓ 正确。
      • (D) 3,2,1：IF1 中 3>2 真、3>1 真 → max←3；接着 IF2 中 2>3 假 → ELSE 执行 max←z=1 ✗ 最大值被覆盖！

      易错点：两个 IF 是并列关系而非嵌套，ELSE 只属于第二个 IF。x 已被正确赋值为 3 后，仍会被 ELSE 强行改写为 1。此题是"用边界输入验证程序正确性"的经典范例——测试不是证明程序对，而是找出程序错的那一刻。

      CED Q11（官方考点：Skill 4.C / CRD-2.I.b；本手册 §4.2，与 AP Classroom 1.4 Q10 同型）

      The following procedure is intended to return the number of times the value val appears in the list myList. The procedure does not work as intended.

      Line 1:  PROCEDURE countNumOccurences(myList, val)
Line 2:  {
Line 3:      FOR EACH item IN myList
Line 4:      {
Line 5:          count ← 0
Line 6:          IF(item = val)
Line 7:          {
Line 8:              count ← count + 1
Line 9:          }
Line 10:     }
Line 11:     RETURN(count)
Line 12: }

      Which of the following changes can be made so that the procedure will work as intended?

      • AChanging line 6 to IF(item = count)
      • BChanging line 6 to IF(myList[item] = val)
      • CMoving the statement in line 5 so that it appears between lines 2 and 3
      • DMoving the statement in line 11 so that it appears between lines 9 and 10
      点击选项作答，选后显示正确答案与解析

      正确答案：C

      解析：本题考查识别并纠正逻辑错误（logic error）。count ← 0（Line 5）写在 FOR EACH 循环内部，导致每次迭代都把 count 清零——最终 RETURN 的只是"最后一次循环的计数（0 或 1）"，而不是 val 出现的总次数。

      修复方法：把初始化语句 count ← 0 移到循环外、过程体内（即 Line 2 与 3 之间），让计数器只初始化一次。这就是选项 (C)。

      逐项排除：(A) 把 item 与 count 比较，逻辑彻底错误；(B) FOR EACH 语法中 item 本身就是元素值而非索引，myList[item] 属越界访问；(D) 把 RETURN 挪进循环会导致第一次比较后就提前返回。

      套路总结：见"计数器结果不对"→ 先查初始化位置（应在循环外），再查自增位置（应在判断内）。这一模式与 AP Classroom 1.4 Q10、以及 2021 年 FRQ 都反复出现。

      Q25（考点：CRD-2.I.1 溢出错误的判定）

      A computer program uses 3 bits to represent integers. When the program adds the decimal (base 10) numbers 5 and 3, the result is 0. Which of the following is the best explanation for the result?

      • AAn overflow error occurred.
      • BA round-off error occurred.
      • CThe result was affected by lossy data compression.
      • DThe result was approximated by a floating-point representation.
      点击选项作答，选后显示正确答案与解析

      正确答案：A

      解析：3 bits 能表示的无符号整数范围是 0~7。5+3=8 超出上限 → 溢出：二进制 101+011=1000，但只有 3 位，最高位 1 被丢弃，剩 000 = 0。这就是溢出错误（overflow error）的标准机制。(B) 舍入误差针对浮点小数；(C) 压缩损失与运算无关；(D) 3 bits 整数与浮点表示无关。与 1.4 Q1（播放量变负数）同考点：整数 + 超范围 = 溢出，是 CRD 每年必考的一分。

      7. Section II 写作题中的 Big Idea 1

      2025 年起 Create PT 取消视频提交，改为提交程序代码 PDF + Personalized Project Reference（PPR），考试当天完成 4 道写作题（占分约 30%）。其中两道直接出自 Big Idea 1：

      7.1 Written Response 1（Program Design, Function and Purpose）

      高频问法（2026 国际考原题）：

      • Describe the overall purpose of your program.（描述程序总体目的）
      • Describe the intended functionality of your program.（描述预期功能——输入是什么、输出是什么）
      • Describe a revision you could make to your program. Explain how feedback or testing could be used as part of a development process for this future revision.

      拿分要点：

      1. 目的 = "解决 …… 问题 / 满足 …… 兴趣"，一句话点明为谁解决什么；
      2. 功能要写清输入 → 处理 → 输出链条；
      3. 修改 + 反馈/测试必须形成闭环："收集反馈/运行测试 → 发现问题 → 修订 → 再次验证"。

      7.2 Written Response 2(b)（Errors and Testing）

      高频问法（2026 国际考原题）：

      • Suppose another programmer modifies your procedure to improve readability without changing behavior. Write a procedure call with specific argument value(s) that can be used to test whether the modified procedure still works as intended. Describe the behavior this call is testing. Explain how this call can be used to test this behavior.

      拿分要点：

      1. 调用必须带具体实参（如 findMin([7, 2, 9, 4])）；
      2. 说明该调用针对哪一种预期行为（"列表无序时应返回最小值 2"）；
      3. 说明判定标准：运行后实际返回值 vs 预期值是否一致，不一致说明修改破坏了功能；
      4. 加分直觉：选边界/极端数据（空表、单元素、含重复最小值的列表）——正是 CRD-2.J.2 的"恰好在或略超出极值"。

      8. 备考策略与应试技巧

      1. 概念题口诀：见到 eliminate / remove the need for / no longer necessary → 高度警惕，多为错误选项（协作不免测试与文档）。
      2. 输入输出题三步法（§2.2）：先定功能 → 再问"缺了它行不行" → 最后分清数据来源（本设备/他人/程序生成）。
      3. 错误类型题先问两个问题：程序能跑吗？（不能→语法错误）数值是整数还是小数？（整数超范围→溢出；小数偏差→舍入）。
      4. 双选题（Select two answers）：CRD 双选题几乎总是一强一强配对（如协作的"多元才能 + 减少偏见"），先锁定两个最贴合 CRD-1/CRD-2 原文的选项，两个都选才得分、选一个不得分。
      5. 代码纠错题必 hand tracing：拿选项里的具体值代进去，逐行填变量表；特别盯"循环变量更新位置"和"RETURN 的位置"。
      6. 写作题提前准备：Create PT 阶段就写好"目的、功能（输入/输出）、一次修改经历、一组测试用例（含过程调用+预期结果）"的素材库，考试时直接套用 PPR 中的代码作答。
